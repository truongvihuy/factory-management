# SRS-04-05. Functional Requirements – Telemetry Management

**Document Name:** Software Requirements Specification (SRS)  
**Section:** SRS-04-05 Functional Requirements – Telemetry Management  
**Project:** Factory Management System (FMS)  
**Version:** 1.0  
**Status:** Draft

---

# 1. Overview

## 1.1 Purpose

This document defines the functional requirements for the **Telemetry Management** module.

Telemetry Management is responsible for receiving, validating, processing, storing, and providing access to real-time telemetry data collected from industrial machines through IoT gateways.

The module serves as the primary data source for Monitoring, Alert Management, Dashboard, Reporting, and Predictive Maintenance.

---

# 2. Business Scope

The module supports:

- Telemetry Collection
- Real-time Data Processing
- Telemetry Validation
- Machine Status Detection
- Historical Telemetry Storage
- Telemetry Query
- Data Aggregation
- Data Archiving

The module does **not** manage alert generation, maintenance scheduling, or reporting logic.

---

# 3. Supported Communication Protocols

The system shall support the following communication protocols.

| Protocol | Purpose |
|-----------|---------|
| MQTT | Primary telemetry communication |
| OPC-UA | Industrial machine communication |
| Modbus TCP | Legacy machine integration |

Additional protocols may be supported in future releases.

---

# 4. Telemetry Data Model

Each telemetry record shall contain at least:

| Field | Description |
|--------|-------------|
| Timestamp | Event timestamp |
| Machine | Source machine |
| Sensor | Source sensor |
| Metric Name | Temperature, Vibration, Energy, etc. |
| Metric Value | Sensor reading |
| Unit | Measurement unit |
| Quality | Good / Warning / Invalid |
| Gateway | Data source gateway |

---

# 5. Functional Requirements

---

# FR-TEL-001 Receive Telemetry

## Description

The system shall receive telemetry data continuously from IoT gateways.

### Supported Sources

- MQTT
- OPC-UA
- Modbus TCP

### Acceptance Criteria

Incoming telemetry is accepted and processed successfully.

---

# FR-TEL-002 Validate Telemetry

The system shall validate:

- Required fields
- Machine existence
- Sensor existence
- Data format
- Timestamp validity
- Duplicate messages (if identifiable)

Invalid telemetry shall be rejected or marked as invalid according to configuration.

---

# FR-TEL-003 Process Telemetry

The system shall process incoming telemetry by:

- Parsing payload
- Normalizing values
- Mapping to machine and sensor
- Updating current machine state
- Forwarding data to downstream modules

---

# FR-TEL-004 Store Raw Telemetry

The system shall store raw telemetry.

Retention:

- Raw Data: 6 Months

Stored data shall remain immutable.

---

# FR-TEL-005 Maintain Current Machine State

The system shall maintain the latest operational state for each machine.

Examples:

- Running
- Idle
- Stopped
- Offline
- Error

Current state shall be updated whenever new telemetry is received.

---

# FR-TEL-006 Historical Telemetry

Users shall view historical telemetry.

Supported filters:

- Time Range
- Factory
- Workshop
- Production Line
- Machine
- Sensor
- Metric Type

---

# FR-TEL-007 Real-Time Monitoring

The system shall continuously update dashboards using the latest telemetry.

Dashboard refresh target:

- Within 1–2 seconds.

---

# FR-TEL-008 Missing Telemetry Detection

The system shall detect missing telemetry.

If telemetry is not received within the configured interval:

- Machine status may become Offline.
- Alert Management may generate alerts.

Detection intervals shall be configurable.

---

# FR-TEL-009 Gateway Synchronization

When communication is interrupted:

- Gateway caches telemetry.
- Cached telemetry is synchronized after reconnection.
- Original timestamps shall be preserved.

---

# FR-TEL-010 Data Aggregation

The system shall generate summarized telemetry.

Aggregation periods may include:

- Minute
- Hour
- Day
- Month

Summary data supports dashboards and reports.

---

# FR-TEL-011 Telemetry Query

Users shall query telemetry by:

- Factory
- Workshop
- Production Line
- Machine
- Sensor
- Metric
- Time Range

Results shall support pagination.

---

# FR-TEL-012 Telemetry Export

Authorized users may export telemetry.

Supported formats:

- CSV
- Excel

Export shall respect authorization rules.

---

# FR-TEL-013 Telemetry Archive

After six months:

- Raw telemetry shall be archived.
- Archived data shall remain searchable.
- Archive operations shall preserve data integrity.

---

# FR-TEL-014 Data Quality Management

Telemetry quality shall support:

- Good
- Warning
- Invalid

Invalid data shall not affect machine status calculations unless configured otherwise.

---

# FR-TEL-015 Machine Status Calculation

The system shall calculate machine operational status based on incoming telemetry.

Status calculation rules shall be configurable.

Examples:

- Running
- Idle
- Stopped
- Offline
- Error

---

# FR-TEL-016 Running Hour Calculation

The system shall calculate machine running hours from telemetry.

Running hour calculations shall support maintenance scheduling.

---

# FR-TEL-017 Energy Consumption Calculation

The system shall aggregate energy telemetry for each machine.

Aggregated values shall support dashboard and reporting.

---

# FR-TEL-018 Telemetry Replay

Authorized users may replay historical telemetry for analysis.

Replay shall preserve the original chronological order of events.

---

# FR-TEL-019 Audit Logging

The system shall record:

- Gateway synchronization
- Manual data import
- Telemetry replay
- Archive execution

System-generated telemetry records themselves are not individually audited.

# 7. Non-functional Considerations

### Performance

- Dashboard updates shall occur within **1–2 seconds**.
- Alert processing shall begin within **3 seconds** after telemetry is received.
- The system shall support processing **30–50 million telemetry records per day** in the initial deployment.
- The architecture shall scale to approximately **500 million telemetry records per day** in future deployments.

---

### Reliability

- Gateway synchronization shall prevent data loss during temporary network outages.
- Original event timestamps shall be preserved after synchronization.
- Telemetry storage shall ensure durability and consistency.

---

### Availability

- Telemetry ingestion services should target **99.99% availability**.
- Historical telemetry shall remain available during normal operations.

---

### Data Integrity

- Raw telemetry records shall be immutable.
- Archived telemetry shall remain searchable.
- Historical data shall never be overwritten.
